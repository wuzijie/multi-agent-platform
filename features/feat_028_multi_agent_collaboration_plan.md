# 多 Agent 协同工作方案

## 一、协同目标

1. **任务分解与分工**：将复杂用户请求拆分为可并行/串行执行的子任务，并按 Agent 能力画像自动分发到最合适模型。
2. **多视角质量保障**：通过执行、评审、裁决、修正的闭环，降低单一模型的偏见与错误率，提升最终交付物质量。
3. **可观测与可追溯**：全链路事件落盘（`logs/events/` + `logs/collab/`），子任务状态写入黑板，支持断点续跑与事后复盘。
4. **弹性与容错**：单点失败可重试、可换模型重分配；超时任务可自动回收，避免悬挂阻塞整体流程。
5. **低耦合可扩展**：新增 Agent/模型、新增 Skill、新增协同模式均通过配置与事件协议接入，不侵入核心调度器。

## 二、典型应用场景

| 场景 | 用户请求示例 | 协同方式 | 参与 Agent |
|------|-------------|----------|-----------|
| 复杂开发任务 | "实现一个支持分页和搜索的 REST API" | 主从编排：规划 → 编码 → 评审 → 汇总 | 克劳德/迪普斯克/钱文 |
| 深度调研报告 | "调研并输出一份 RAG 技术深度报告" | Skill 事件闭环：维度拆解 → 多模型并行调研 → 汇总 → 交叉审核 → 迭代终稿 | 全部在线模型 |
| 方案评审决策 | "这个架构设计是否合理" | 多模型讨论：主机回答 → 多 Agent 评审 → 多轮修订 | 用户@的 2+ Agent |
| 模型间转交 | "@吉米 帮我总结这份长文档" | 共享消息总线：Agent 通过 `@Agent名` 主动转交 | 任意 Agent |
| 事件驱动批量处理 | "把这份需求拆成子任务并行执行" | DAG 调度 + 事件总线 + 黑板状态 | 调度器统一分配 |

### 3.1 核心数据流

```
用户请求
  → Orchestrator 模式路由
    ├─ 简单/单 Agent          → AgentRuntime 直接执行
    ├─ @mention 单 Agent      → AgentRuntime + @提取与转交
    ├─ @多 Agent 讨论         → 讨论模式闭环
    ├─ skill=deep_research    → DeepResearch 5 步事件闭环
    └─ collab_mode=event-driven → Scheduler DAG 事件驱动闭环

事件驱动闭环：
  TASK_CREATE_EVENT → 主 Agent/调度器生成 DAG
  → 批量写入子任务 (PENDING)
  → 依赖就绪检测
  → 能力画像匹配 Agent
  → SUB_TASK_DISPATCH (RUNNING)
  → Agent 流式执行
  → SUB_TASK_SUCCESS / FAIL
  → 更新黑板 / 触发下一轮就绪
  → TASK_ALL_FINISH → 汇总 → 写入对话
```

## 四、协同模式选型

### 4.1 主从编排（Master-Slave Orchestration）

**定义**：由主 Agent（默认克劳德）担任规划者和收口者，其他 Agent 担任执行者/评审者。

**适用**：有明确阶段边界的复杂任务（规划→执行→评审→汇总）。

**实现要点**：
- 主 Agent 将用户请求拆分为带依赖的 JSON DAG，每个子任务指定执行模型。
- 调度器负责解析 DAG、按依赖驱动、分配 Agent、重试与超时回收。
- 上游子任务输出注入下游子任务上下文（`scheduler.js` 中 `_dispatchSubTask`）。
- 失败时回退默认 DAG，保证最低可用。

### 4.2 事件驱动（Event-Driven Collaboration）

**定义**：所有状态变更通过事件总线广播，调度器作为唯一状态决策者，Agent 只执行不维护状态。

**适用**：多子任务并行、需要实时右侧任务面板、支持多轮对话的协作。

**实现要点**：
- 事件协议定义于 `src/engine/events.js`：TASK_CREATE / PLAN_FINISH / SUB_TASK_SUCCESS / FAIL / RETRY / CANCEL / ALL_FINISH。
- 黑板作为共享状态存储：`blackboard:task:{trace_id}:main|sub:*`。
- 幂等去重：`blackboard:idempotent:{msg_id}`。
- 僵尸检测：`blackboard:running:{sub_id}` TTL 标记。
- 右侧任务面板通过 `collab:subtask:update` 事件实时刷新。

### 4.3 共享消息总线（Shared Message Bus）

**定义**：所有 Agent 通过统一事件总线收发消息，支持 Agent 主动 `@Agent名` 转交问题。

**适用**：开放式多轮对话、模型间自主协作、动态路由。

**实现要点**：
- `src/eventbus/bus.js`：内存 EventEmitter + 文件持久化。
- Agent 回复中的 `@Agent名 问题` 由 Orchestrator 提取并转发。
- 最多 3 跳防死循环，已访问 Agent 不再重复访问。
- 流式输出通过 `agent:stream:start/chunk/end` 推送到前端。

### 4.4 模式对比与选型建议

| 维度 | 主从编排 | 事件驱动 | 共享消息总线 |
|------|---------|---------|-------------|
| 控制权 | 主 Agent 强控制 | 调度器统一控制 | 各 Agent 自治 |
| 适用任务 | 阶段明确、可拆分 | 复杂、多子任务 | 开放对话、探索式 |
| 状态位置 | 黑板 + 调度器内存 | 黑板 | 对话记录 + 事件文件 |
| 可观测性 | 高（DAG + 面板） | 高（事件流） | 中（对话流） |
| 扩展方式 | 新增 TASK_TYPES | 新增事件类型 | 新增 Agent/触发词 |

**推荐组合策略**：
- 简单问答 → 单 Agent 直接执行。
- 明确复杂任务 → 事件驱动 + 主从编排混合（主 Agent 规划 DAG，调度器事件驱动执行）。
- 调研/报告类 → 标准化 Skill（DeepResearch）。
- 开放式讨论 → 多模型讨论模式或 @mention 消息总线。

### 5.3 风险与约束

1. **模型调用超时**：CLI 启动 + 模型生成总时间可能超过 240s，长任务仍存在失败风险。
2. **上下文长度**：上游输出注入下游时当前限制 8000 字符，超长 DAG 可能需要摘要或 RAG。
3. **黑板文件 I/O**：高并发下文件读写可能成为瓶颈，后续可平滑替换为 Redis。
4. **能力画像静态化**：当前能力基于 `agents.yaml` 配置，未根据历史执行表现动态更新。

## 六、下一阶段演进方向

1. **人工介入点**：在评审失败或关键节点允许用户选择「通过 / 重试 / 跳过 / 指定 Agent」。
2. **动态能力画像**：根据 Agent 历史成功率、延迟、负载更新画像权重。
3. **更多标准化 Skill**：代码审查、测试生成、文档生成等。
4. **持久化层可插拔**：黑板接口抽象，支持从文件版无缝切换到 Redis。
5. **跨任务经验复用**：将成功 DAG / Skill 模板沉淀为可复用工作流。
