# 动态上下文管理方案

> 目标：把「@ 转交」从"只传一句话任务描述"升级为**带投递游标的增量上下文接力**，并对 agent 间的来回拉扯（乒乓）做软治理：**同一对 agent 来回 ≥2 次注入警告，≥4 次直接阻断**。
>
> 状态：方案稿（未实现）。所有文件名/函数名均对应本仓库现有代码。

---

## 1. 背景与现状问题

当前 @ 机制（`src/messaging/mention.js` + `src/orchestrator/execution.js::_runAgentWithHandoff`）存在三个问题：

1. **上下文断裂**：被 @ 的 agent B 只收到 A 写的「任务描述」一行指令，看不到 A 的完整回复（分析过程、结论、@ 上下文），也不知道自己处在接力链的什么位置。
2. **治理手段太硬**：链式转交靠 `max_hops=3` + `visited` 集合拦截——同一条链上每个 agent 只能出现一次，A→B→A 这种"回马枪"根本走不到，无法表达"允许来回但要收敛"的语义；也防不住两个 agent 之间只针对封闭问题的低效拉扯（如果放开 visited，又会无界循环）。
3. **上下文成本失控**：要么不带历史（B 失忆），要么全量注入（token 爆炸）。缺少"按未读增量投递 + 预算裁剪"的机制。

本方案对应三件事：

- **增量上下文组装**（`assembleIncrementalContext`）：被 @ 时按六段结构组装 prompt；
- **Delivery Cursor**：每只 agent CLI 一个独立投递游标，只看到自己没看过的消息；
- **乒乓治理**：同一对 agent 来回次数达阈值时警告/阻断（通过注入 prompt 实现，阻断时不发起调用）。

---

## 2. 总体数据流

```
用户消息
  → parseMentions()                        （mention.js，不变）
  → 创建 handoff job（含 task_id、turn_id、from=用户）
  → assembleIncrementalContext(target=B)   （新模块，本方案核心）
      ├─ 来源标识 / 模式声明 / 导航头 / 触发原文
      ├─ 未读历史（delivery_cursor 之后，Warm/Cold 二选一，预算裁剪）
      └─ 系统提示 + 条件注入的乒乓警告（≥2 次时）
  → renderer 渲染 → adapter.execute()      （prompt 走 stdin）
  → B 的回复写入 messages.jsonl（seq++）
  → 解析 B 回复中的行首 @ → 下一跳（携带乒乓计数）
  → 投递成功后推进 B 的 delivery_cursor
```

## 3. 消息模型扩展

`tasks/<taskId>/messages.jsonl` 每条消息追加字段（向后兼容，缺省值即现状）：

```json
{
  "seq": 42,                    // 已有：单调递增
  "ts": "...",                  // 已有
  "role": "user|assistant|system",   // 已有
  "agent": "克劳德",             // 已有：assistant 的发言者 / 转交链 user 消息的发送者
  "kind": "chat|briefing|whisper|display|backfill",  // 扩展：默认 chat
  "visible_to": null,           // 扩展：whisper 专用，数组，null=所有人可见
  "turn_id": "turn_xxx",        // 扩展：本轮用户消息开启的轮次 ID
  "from_agent": "克劳德",        // 扩展：转交链上一条消息的发送者（触发者）
  "content": "..."
}
```

| kind | 语义 | 是否投递 |
|---|---|---|
| `chat` | 正常对话消息 | 是 |
| `system` / `display` | 系统展示消息（conversation.md 中的 ⚙️ 提示） | 否（role=system 一律过滤） |
| `briefing` | Cold Path 生成的简报 | 否（简报是投影，原文仍按 kind=chat 投递；简报本身不再二次投递） |
| `whisper` | 定向私语 | 仅 `visible_to` 包含目标 agent 时投递，其余 agent 不可见 |
| `backfill` | 老会话回填 | 同 chat |

改动点：`message-log.js::append()` 增加 `kind/visible_to/turn_id/from_agent` 参数；新增查询：

```js
// 取某 agent 的未读消息（投递语义，区别于 resume 用的 since()）
unread(taskId, { cursorSeq, agent, turnId })
// 过滤规则：
//   seq <= cursorSeq                      → 已读，跳过
//   role === 'system'                     → 系统展示消息，跳过
//   kind === 'display' | 'briefing'       → 跳过
//   kind === 'whisper' 且 visible_to 不含 agent → 跳过
//   role === 'assistant' 且 agent === 自己 → 跳过（自己的输出）
```

## 4. Delivery Cursor（投递游标）

### 4.1 定义

每个 agent 在 `tasks/<taskId>/cli_state/<agent>.json`（`cursor-store.js`）中增加一个字段：

| 字段 | 语义 | 现有/新增 |
|---|---|---|
| `cursor_seq` | resume 增量用的"已写进 CLI session 的进度" | 已有 |
| `delivery_cursor` | 投递游标：该 agent 已收到过的最大消息 seq | **新增** |
| `pingpong` | 本对话内与其他 agent 的往返计数（可选持久化） | **新增** |

两者分开的原因：`cursor_seq` 服务于 `--resume` 的 delta 计算（`runtime.js`），session 失效时会清零重放；`delivery_cursor` 服务于"投递了哪些消息"的语义，即使 resume 失效、走全量注入，也不应把已经投递过的消息当成"未读"重复轰炸。

### 4.2 推进时机

- **成功或取消**：完整投递后（`status === success` 或 `cancelled`）推进到最后一条投递消息的 seq。
- **失败**：不推进，下次重发同样的未读。
- **阻断**：不调用、不投递，游标不动。
- 并行 @ 多个目标时各自独立推进，互不影响。

### 4.3 与 resume 的关系

`runtime.js` 中 delta 模式现在用 `messageLog.since(task_id, cursorState.cursor_seq, {excludeAgent: agentName})`。改造后：

- 本方案的未读历史统一以 `delivery_cursor` 为准（`messageLog.unread`）；
- resume 的 `cursor_seq` 继续用于 CLI session 的增量发送，但**发给 CLI 的未读历史只取 `delivery_cursor` 之后的部分**，避免同一批消息既被 session 记过又被 prompt 重复注入；
- 首次调用（无 session）：`delivery_cursor = 0`，但未读历史按 Warm/Cold 与预算限量，不无脑全量。

### 5.2 Prompt 分段结构（按输出顺序）

```

[模式声明] 你是本轮第 2 只被召唤的 agent（串行接力模式）

  <delivery_cursor 之后的未读消息，Warm 展开 / Cold 简报>
[系统提示]
  ├ 传球决策树：继续 @（谁、为什么）/ 收尾直接回复用户 / 请求人工介入
  ├ 队友花名册：可 @ 的 agent 列表（名字/模型/能力/当前忙闲/剩余可召唤次数）
  ├ 协作格式：行首 @ + 下一行描述；@ 块只能在首/尾；每人最多 @ 2 个；不能 @ 自己
  └ 球权检查：接力棒现在在你手里；你本轮已被召唤 N 次；与克劳德已来回 K 次
[乒乓警告]（条件注入：与 A 的往返 ≥2 次）
  你与 克劳德 在本轮已来回 3 次。请立即收敛：要么给出结论并结束，
  要么 @ 一位第三方 agent 接手；不要再次 @ 克劳德。
```

各段落的说明：

| 段落 | 内容 | 数据来源 |
|---|---|---|
| 来源标识 | `Direct message from <A> [model=<CLI 侧模型名>]` | fromAgent + agents 配置 |
| 模式声明 | "你是第 N 只被召唤的 agent CLI"（N = 本轮 spawning 序号）；串行接力模式下显式声明 | turn 上下文计数器 |
| 导航头·接力棒 | A → 你，跳数，链上路径 | turn 上下文（lineage） |
| 导航头·活跃任务 | collab/黑板的子任务状态摘要 | `scheduler.getTaskState()` / collab state |
| 导航头·最近修改文件 | `git status --short` 限量 + workspace 最近 mtime | 一次性采样缓存（每次组装只跑一次） |
| 触发原文 | A 的完整回复（含 @ 行）；超长时头尾截断（首 4000 + 尾 2000 字符，中间标注省略） | triggerMsg.content |
| 未读历史 | 见 §6 Warm/Cold | `messageLog.unread()` |
| 系统提示·传球决策树 | 何时继续传、何时收尾的判定规则 | 模板文件 |
| 系统提示·队友花名册 | agent 名单 + 能力 + 忙闲 + 本轮剩余可召唤次数 | `agent-list.js` + turn 上下文 |
| 系统提示·协作格式 | 现有 @ 规则（行首、首尾放置、最多 2 个、不自 @） | 与 `renderer.buildStableContext` 现有文案对齐，避免重复两套规则 |
| 系统提示·球权检查 | "接力棒在你手里"，防止 agent 误以为在旁听 | turn 上下文 |
| 乒乓警告 | 条件注入（见 §7） | turn 上下文计数 |

### 5.4 与现有 ZONE A/B/C 的关系（通用应用范围）

现有结构（`runtime.js`）：

- ZONE A：工具说明 + 稳定上下文（团队规则/目标/记忆）——保持不变；
- ZONE B：历史——**由本方案的「导航头 + 系统提示 + 未读历史」替换**；调用方另有转录历史（`history_segments`，如讨论/DAG 场景）时，以「转录历史」段并入，避免上下文断裂；
- ZONE C：本轮 instruction——改为「来源标识 + 模式声明 + 触发原文 + 任务描述」。

**通用应用**：增量上下文不止用于 agent → agent 转交，而是所有模型调用场景默认注入：

| 场景 | 触发者（来源标识） | 触发原文 | 组装位置 |
|---|---|---|---|
| 聊天直呼（用户 @ / 普通对话） | 用户 | 本轮指令 | runtime 自动组装 |
| agent → agent @ 转交 | 上一棒 agent | A 的完整回复 | execution 显式组装（带接力链/乒乓计数） |
| 讨论模式 / 三类协作模式 | 协作流程 | 当前阶段指令 | runtime 自动组装 |
| DAG 子任务 / 规划 | 调度器 | 子任务指令 / 规划 prompt | runtime 自动组装 |

- 统一入口 `src/prompt/incremental.js::buildIncrementalContext`：会话键取 `external_task_id || task_id`，未读按（会话, agent）的 delivery_cursor 取，成功后才推进；
- 调用方显式传 `task.incremental_context` 时以显式内容优先（execution 的转交链）；
- 后台维护类调用（会话记忆摘要、长期记忆提炼）设 `task.skip_incremental_context = true` 关闭注入。

代价说明：未读历史是动态的，会破坏 KV 前缀缓存的部分命中。取舍：投递语义优先；把相对稳定的段落（系统提示、导航头）放在未读历史之前，尽量提高公共前缀命中率。工具回灌轮仍在同一轮内追加，轮内前缀不变。

### 5.5 resume 增量：第二次调用起只发增量

CLI 通过 `--resume` 保存了前轮上下文（固定头部、ZONE A 稳定上下文、前几轮的六段式内容都已在其 session 里）。因此 **resume 生效时（同一会话第 2 次调用起）只发增量内容**：

```
[执行许可]          每轮必须（许可状态可能变化）
[未读历史]          delivery_cursor 之后的新消息（Warm/Cold 预算规则不变）
[本轮指令]          本轮 task.instruction（当前要处理的事）
[乒乓警告]          条件注入（与触发者来回 ≥ warn_threshold）
```

跳过：来源标识、模式声明、导航头、触发消息原文（其在未读历史里以发送者标签呈现）、系统提示（决策树/花名册/协作格式/球权检查）——这些首轮已发过，CLI session 内已有。

实现：`runtime` 先计算 `resumeActive`，命中时用 `buildIncrementalContext({ delta: true, instruction })` 组装；首次调用/无 resume（含 `__forceFull` 重试）/resume 准入未通过时走完整六段式。execution 的转交链同时携带 `trigger_from/trigger_content/incremental_turn` 等元信息，供 runtime 在 resume 模式下重建 delta。

## 6. Warm Path 与 Cold Path

### 6.1 判定（配置可调）

```
未读条数 ≤ warm_max_msgs（默认 12） 且 总字符 ≤ warm_max_chars（默认 12000）
  → Warm Path
否则
  → Cold Path
```

### 6.2 Warm Path：直接展开

逐条格式化：

```
[#41 用户] ……
[#42 克劳德 → 你] ……（这条 @ 了你）
[#43 迪普斯克] ……
```

每条消息按发送者标注：用户 / agent 名 / 谁 @ 了你。代码块消息保持原样（不截断）。

### 6.3 Cold Path：生成简报

两种实现，配置切换：

1. **确定性简报（默认，零模型成本）**：
   - 按参与者归纳：`【克劳德】共 12 条，最后一次发言 #88：<关键结论行（优先取"结论：/总结：/最终"开头的行）>`;
   - 抽取所有 @ 关系：`谁 @ 了谁 + 任务描述（各 1 行）`;
   - 附"问题演进"时间线（每条取首 120 字符）；
   - 总量 ≤ `cold_brief_max_chars`（默认 2500）。
2. **LLM 摘要（可选，`cold_use_llm: true`）**：调用一次轻量模型（默认钱文/qwen）生成 ≤600 字简报；失败/超时自动回退到确定性简报。

Cold 之后 `delivery_cursor` 同样推进到最后一条；原始消息保留在 messages.jsonl，后续可追溯。

## 7. 乒乓治理（警告 + 阻断）

### 7.1 计数口径

- 键：**无序对** `pairKey = [A, B].sort().join('|')`，值：本对话内该对 agent 的往返次数；
- 往返定义：A 的回复 @ 了 B 且 B 被执行（计 1 次），B 的回复又 @ 了 A 并被执行（再计 1 次）。即"同一对 agent 相互召唤的次数"。
- 计数作用域：**本轮（turn_id）内**。新一轮用户消息开启的 turn 计数清零；跨轮的历史计数可作为参考写入球权检查，但不触发警告/阻断。
- 存储：turn 上下文对象（`_executeTurnWithJobs` 内存）+ 可选持久化到 `cli_state/<agent>.json` 的 `pingpong` 字段（覆盖同轮崩溃恢复的场景）。

### 7.2 阈值与行为

| 往返次数（同一对） | 行为 |
|---|---|
| 1 | 正常投递 |
| **≥2（warn_threshold）** | 投递正常 + prompt 注入 **[乒乓警告]** 段（告诉模型已来回几次、要求收敛） |
| **≥4（block_threshold）** | **阻断**：不 spawn CLI；把 A 回复中的该 @ 忽略；向 messages.jsonl 写一条 system 消息 `[转交阻断] 克劳德 ↔ 迪普斯克 已来回 4 次，本轮禁止继续互传`；conversation.md 同步展示；返回 `{ok:false, blocked:true}` |

阻断是"软阻断"：只砍这一条 @ 边，不影响本轮其他分支；被阻断的 agent 不消耗 token。

### 7.3 与现有 max_hops / visited 的改造

现状（`execution.js`）：

```js
const visited = new Set(jobs.map(j => j.agent));   // 链上已出现的 agent 不再接收
budget = { left: maxSpawns }                        // max_spawns_per_turn = 6
maxHops = 3
```

矛盾：`visited` 会让 A→B→A 在第二跳就被丢弃，乒乓计数永远到不了 2。改造：

- **移除 `visited` 去重**（同一 agent 可被多次召唤）；
- `max_hops` 从 3 放宽为 **6**（硬上限兜底，防环爆炸）；
- 新增 `summon_max_per_agent`（默认 4）：同一 agent 单轮被召唤超过 N 次也阻断（与乒乓计数互补）；
- 保留 `max_spawns_per_turn`（6）作为总预算。

### 7.4 配置

`config/mention.yaml` 追加：

```yaml
mention:
  max_hops: 6                 # 由 3 放宽
  summon_max_per_agent: 4

pingpong:
  warn_threshold: 2           # 同一对 agent 来回 ≥2 次：注入警告
  block_threshold: 4          # ≥4 次：阻断该 @ 边

context:
  warm_max_msgs: 12
  warm_max_chars: 12000
  cold_brief_max_chars: 2500
  cold_use_llm: false
  budget_ratio: 0.5           # 未读历史最多占"可用预算"的 50%
  model_cap_default: 128000   # 模型输入 token 上限默认值（可按 CLI 覆盖）
```

## 8. Token 预算分配

### 8.1 公式

```
可用预算 = model_cap × budget_ratio_effective
        = model_cap
        − 固定开销（系统提示 + 工具说明 + 稳定上下文 + 模板骨架 + 预留输出 max_tokens）
fixed_parts 按实际渲染长度估算（字符/3 近似 token），
剩余部分 = 可用预算 − 固定段 → 分配给未读历史。
```

`model_cap` 来源：`config/context.yaml`（或按 agent 在 agents.yaml 中覆盖），默认 128k；未知 CLI 一律用默认值。

### 8.2 裁剪规则

- 顺序：必需段（来源/模式/导航/触发原文/系统提示/警告）先占预算；
- 未读历史**从最新向最老保留**，超预算时**从最旧的消息开始丢弃**（丢弃整条消息，不截半条）；
- 因预算丢弃了 N 条时，在未读历史尾部追加一行：`（更早的 K 条消息因预算省略）`;
- 触发原文超长时做头尾截断（首 4000 + 尾 2000 字符），标注省略位置。

## 10. 边界与降级

- **resume 与投递游标并存**：见 §4.3；session 失效走全量时不得把已投递消息算作未读。
- **whisper 可见性**：`visible_to` 不含目标的 whisper 不投递；组装器过滤后若未读为空，输出"（无新消息）"。
- **系统展示消息与 briefing**：一律过滤；briefing 只写 conversation 展示，不进入任何投递。
- **模型上限未知**：默认 128k；裁剪兜底保证不会超长。
- **失败重试**：投递游标只在成功/取消后推进；阻断不推进。
- **多 @ 并行**：每个目标独立组装、独立游标、独立乒乓计数（按 pair）。
- **阻断后的展示**：A 的回复正常展示，其被阻断的 @ 以系统消息说明原因；与现有"违规转交已忽略"的降级风格一致。
- **性能**：`git status` 采样每轮只跑一次并缓存；Cold 简报为纯函数路径，无模型调用。

## 11. 实施阶段

| 阶段 | 内容 | 验收 |
|---|---|---|
| P1 | 消息模型扩展 + delivery_cursor + assembleIncrementalContext（仅 Warm Path）+ 模板 + 单测 | 目标 agent 收到六段结构；过滤生效；游标断点重发不丢消息 |
| P2 | Cold Path（确定性简报）+ Token 预算与裁剪 | 100 条未读走 Cold，简报 ≤2500 字，超预算丢最旧 |
| P3 | 乒乓计数（警告 ≥2 / 阻断 ≥4）+ visited 改造 + 配置 | A↔B 第 2 次收到警告；第 4 次不再 spawn，出现阻断系统消息 |
| P4 | 真实 CLI 联调 + 会话日志 delivery 事件 + 前端展示"第 N 个被召唤/已阻断" | 端到端场景通过（见 §12） |

每阶段独立可上线；P1/P2 先于 P3 落地也能获得收益（上下文质量提升），P3 只依赖 turn 上下文，风险最小。

## 12. 验收场景

1. **增量投递**：用户 @克劳德 → 克劳德 @迪普斯克。迪普斯克的 prompt 含来源标识（克劳德 + 模型名）、模式声明（第 2 只）、导航头、克劳德完整回复、系统提示；未读历史不含自己旧输出与系统消息。
2. **乒乓警告**：A↔B 第 2 次往返，B 的 prompt 出现 [乒乓警告]（次数、收敛要求）。
3. **乒乓阻断**：A↔B 第 4 次往返，B 不再被拉起；messages/conversation 出现「转交阻断」系统消息；该分支返回 `blocked:true`，其余分支不受影响。
4. **Cold Path**：构造 100 条未读，判定为 cold，简报 ≤2500 字，prompt 总量不超过模型预算；丢最旧而非丢最新。
5. **游标**：一次调用失败后重发，未读消息不丢失；成功后游标推进，不重复投递。
